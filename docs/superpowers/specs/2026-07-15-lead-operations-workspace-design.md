# Lead operations workspace v2 - design spec

Date: 2026-07-15. Approved direction: **B, guided operator workflow**.
Product context: Ruumly is a demand-first concierge. This work improves the manual
request -> provider outreach -> customer offer -> confirmed booking loop after the first
real lead exposed operational gaps.

## 1. Outcome

An admin can take one customer request from arrival to a confirmed outcome without
guessing what any action does:

1. Find every relevant provider, including nearby municipalities.
2. Search the complete active provider directory and select any provider manually.
3. Review the exact provider outreach before sending it.
4. Track replies and turn confirmed providers into customer offer options.
5. Preview the exact customer email and offer page without fabricating a view receipt.
6. Delete an abandoned draft safely.
7. Send the offer and see what state changes.
8. Record the customer's preferred option without calling it a booking.
9. Mark the lead booked only after Ruumly confirms with the provider.

The workspace stays suitable for the first ten leads: guided and explicit, but not a
general CRM.

## 2. Evidence and root causes

Production currently has seven warehouse providers within 8.4 km of central Tartu:
four tagged `Tartu`, plus Vahi (4.6 km), Tõrvandi (6.9 km), and Reola (8.4 km).

The current matcher is structurally unable to present that set reliably:

- It ranks exact city-string equality, not geographic distance.
- It takes listing rows before directory suppliers.
- The ten-row cap applies before suppliers are deduplicated, so multiple listings from
  one supplier can consume the result budget.
- It has no search or explicit "all providers" path in the admin workspace.

The offer workflow has three separate contract problems:

- The admin's draft "Open offer page" link points to a public endpoint that deliberately
  returns 404 for drafts.
- There is no draft-delete endpoint or control.
- The send confirmation shows only an option count, not the recipient, subject, email,
  customer page, or resulting state changes.

Finally, public `ChooseOption` currently changes the lead to `Converted`. That counts a
customer preference as a booked customer before Ruumly confirms with the provider.

## 3. Operator experience

The expanded lead becomes a three-stage workspace. On mobile the stages stack in order;
on desktop stages 1 and 2 may share the work area, but the sequence remains visible.

### Stage 1 - Find and contact providers

- Header: lead age, service, route/city, date, and response SLA.
- Search input: supplier name, location name, city, address, email, or phone.
- Scope control: `Nearby (25 km)` and `All Estonia`.
- Category defaults to the lead's service. In `All Estonia`, an explicit `All services`
  control may remove that filter when the request is ambiguous; nearby discovery never
  broadens categories implicitly.
- Results are unique suppliers, not listing rows.
- Each row shows the closest relevant location, exact distance when available, service
  coverage, email/phone, and whether outreach has already been sent.
- A supplier with several locations expands to show the other locations. Outreach remains
  one email per supplier; a chosen location can seed an offer option.
- Providers without email remain visible with call/copy actions but cannot be selected for
  bulk email.
- Main action: `Review message to N providers`.

The review sheet shows every recipient and the exact localized subject/body generated by
the backend. Confirming sends the batch. Previously contacted providers are skipped by
default; a separate explicit resend action is available from their outreach-history row.

### Stage 2 - Build customer options

- Outreach history shows Sent, Replied, Declined, and No answer with notes.
- Replied providers have a prominent `Add to offer` action, but admin can add any provider
  or a free-form option when a quote arrived through another channel.
- One current draft is presented at a time. Creating while a draft already exists returns
  that draft instead of creating an invisible duplicate.
- The option editor keeps title, provider/location, price, unit, notes, and ordering.
- `Delete draft` is destructive-looking, requires confirmation, and is available only for
  a Draft offer. Sent, Viewed, Chosen, and Expired offers are immutable to deletion.
- Previous sent/closed offers are shown as compact history, not loaded into the active
  editor accidentally.

### Stage 3 - Review and send

`Review delivery` opens an admin-only preview with two views:

1. **Email:** exact recipient, localized subject, and exact text body.
2. **Customer page:** the same sanitized data and visual component used by the public
   offer page.

Previewing never marks the offer Viewed. The broken draft public link is removed.

The final confirmation states the effects explicitly:

- email is sent to the displayed address;
- the customer link becomes live;
- the lead moves to Quoted;
- opening the public link records Viewed;
- requesting an option records a preference and alerts Ruumly;
- no payment or confirmed booking happens at that point.

After the customer requests an option, the workspace shows `Customer selected` and the
chosen option. Admin then uses `Confirm with provider and mark booked`; only that action
moves the lead to Converted.

## 4. Geographic provider discovery

### Candidate sources

Build one candidate set from active suppliers that satisfy either condition:

- they have an active listing matching the lead category; or
- they are an active directory supplier whose `ServiceTypesJson` contains the category.

For an `Any` lead, include every active supplier. Deduplicate by `Supplier.Id` before any
limit is applied.

### Locations and anchor

Use active `SupplierLocation` coordinates. For a legacy listing-only supplier without a
location, fall back to the matching listing's city/address/coordinates.

Resolve the lead's city anchor without an external geocoder:

1. Collect valid coordinates for active locations/listings whose city equals the lead city
   case-insensitively.
2. Use their average latitude/longitude as the city anchor.
3. If no anchor can be derived, rank exact-city results first and return distance as null;
   the all-provider search remains fully usable.

For every supplier, select the nearest relevant location to the anchor using Haversine
distance. Sort exact-city first, then distance, then supplier name. The default nearby
scope is 25 km. Search within `All Estonia` is never distance-restricted.

### API

Add a backward-compatible endpoint rather than breaking the existing array response:

`GET /api/admin/leads/{id}/provider-candidates`

Query parameters:

- `q` optional search text;
- `scope=nearby|all`, default `nearby`;
- `category=lead|any`, default `lead`; `any` is accepted only with `scope=all`;
- `radiusKm`, default 25, clamped to 1..250;
- `limit`, default 50, clamped to 1..200.

`category=lead` applies the lead category rules above. `category=any` searches every
active supplier regardless of service type and is the API contract behind the explicit
`All services` control. Combining `category=any` with `scope=nearby` returns 400 so an
operator cannot accidentally contact unrelated nearby businesses.

Response:

```json
{
  "items": [
    {
      "supplierId": "guid",
      "supplierName": "Rare Minilaod",
      "contactEmail": "...",
      "contactPhone": "...",
      "serviceTypes": ["warehouse"],
      "locationId": "guid",
      "locationName": "Rare Minilaod",
      "city": "Tartu",
      "address": "Pikk 40, Tartu",
      "lat": 58.38209,
      "lng": 26.735605,
      "distanceKm": 0.6,
      "isExactCity": true,
      "listingId": null,
      "listingTitle": null,
      "price": null,
      "priceUnit": null,
      "alreadyContacted": false,
      "lastOutreachAt": null,
      "otherLocations": []
    }
  ],
  "total": 7,
  "scope": "nearby",
  "radiusKm": 25,
  "anchor": { "lat": 58.377953, "lng": 26.729002 }
}
```

Keep `GET /api/admin/leads/{id}/matches` operational for compatibility; internally it may
reuse the new matcher and return its first ten items in the legacy shape.

## 5. Outreach delivery contract

Add:

`POST /api/admin/leads/{id}/outreach/preview`

Body:

```json
{ "supplierIds": ["guid"] }
```

It returns recipients with supplier id/name, email, language, subject, text body, and any
skip reason. It has no persistence or email side effect.

Extend the existing send body to:

```json
{ "supplierIds": ["guid"], "resend": false }
```

When `resend=false`, suppliers already contacted for the lead are returned as skipped with
reason `already_contacted`. When `resend=true`, a new outreach row and email are created.
Save all rows before enqueueing emails, preserving the existing transaction ordering.

The preview and send paths use one shared composer, so previewed text cannot drift from
delivered text.

## 6. Offer lifecycle contract

### Draft handling

- `POST /api/admin/leads/{id}/offers` returns the existing newest Draft for that lead when
  one exists; otherwise it creates one.
- `DELETE /api/admin/offers/{id}` deletes only Draft offers and their options, audits the
  action, and returns 204.
- Deleting any other status returns 409.

### Delivery preview

Add:

`GET /api/admin/offers/{id}/delivery-preview`

Response:

```json
{
  "recipient": { "name": "Mari", "email": "mari@example.com" },
  "email": { "subject": "...", "textBody": "..." },
  "page": { "status": "draft", "language": "et", "lead": {}, "options": [] }
}
```

Extract shared projections/composers so this endpoint, SendOffer, and the public offer page
derive their data and email content from one implementation. Admin preview never changes
offer status or timestamps.

### Customer selection and confirmation

Public `POST /api/offers/{token}/choose` continues to set Offer.Status=Chosen and the chosen
fields, remains idempotent for the same option, and alerts the ops inbox. It no longer moves
the DemandLead to Converted. The lead remains Quoted.

Add:

`POST /api/admin/offers/{id}/confirm-booking`

Requirements:

- offer must be Chosen;
- chosen option must still exist;
- action is idempotent;
- move the DemandLead to Converted using `DemandLeadLifecycle`;
- audit who confirmed it;
- do not create a marketplace Booking, Order, payment, or contract automatically.

The native marketplace commerce layer remains available when an operator deliberately uses
it; this concierge confirmation is only the demand-funnel outcome.

## 7. Frontend structure

Reduce `AdminLeads.tsx` responsibility while preserving the existing lead list and filters:

- `LeadWorkspace.tsx`: orchestration, lead status, stage state, shared query invalidation.
- `LeadProviderStage.tsx`: provider search, scope/radius, selection, outreach review.
- `LeadOfferStage.tsx`: outreach history, active draft, option editing, draft deletion.
- `LeadDeliveryReview.tsx`: exact email/page preview, send effects, final confirmation.
- `LeadActivityTimeline.tsx`: compact lifecycle history.
- `OfferPresentation.tsx`: shared customer-facing option presentation used by the public
  page and admin preview.

This is an operational surface: restrained colors, compact controls, visible state, no
cards nested inside cards. Repeated provider/option rows may be framed; stages use dividers
and full-width bands. Touch targets are at least 44 px on mobile, keyboard focus is visible,
and destructive actions use explicit confirmation.

All new copy is localized in et/en/ru/lv/lt. Customer-facing wording uses `Request this
offer`, not `Choose this option`, and states that no payment or booking occurs until Ruumly
confirms with the provider.

## 8. State flow

```text
Lead New
  -> outreach sent -> Lead Contacted
  -> offer sent    -> Lead Quoted, Offer Sent
  -> page opened   -> Lead Quoted, Offer Viewed
  -> option request-> Lead Quoted, Offer Chosen
  -> admin confirms-> Lead Converted (booked outcome)
```

Dismissed and Unmatched remain existing terminal paths. A customer selection is visible in
the funnel but is not counted as a booking.

## 9. Error and concurrency behavior

- No city anchor: show exact-city/search results and `Distance unavailable`; never return
  an empty workspace merely because coordinates are absent.
- Missing provider email: show the provider and call/copy actions; preview/send reports
  `no_email`.
- Duplicate outreach: skip unless the admin explicitly resends.
- Stale/chosen offer: 409, invalidate and reload the workspace.
- Draft deleted in another session: 404, close the editor and refresh offer history.
- Preview failure: keep the draft intact and show a retryable error; never fall back to the
  public draft URL.
- Send validation failure: remain in review with the exact missing requirement highlighted.
- Email queue failure follows existing durable background-job handling; the saved state and
  audit trail remain authoritative.
- Confirm-booking retries are idempotent and never regress a Converted lead.

## 10. Testing and release gates

### Backend

- Candidate matcher returns seven unique warehouse suppliers for the Tartu/Vahi/Tõrvandi/
  Reola fixture ordered by distance.
- Duplicate listing rows do not consume supplier slots.
- Nearby radius and all-Estonia search behave independently.
- Missing coordinates fall back to exact-city/name sorting.
- Outreach preview is side-effect-free and byte-for-byte matches the sent subject/body.
- Duplicate outreach skips; explicit resend creates a second row.
- Existing Draft is reused; Draft delete cascades options; sent delete returns 409.
- Delivery preview does not set ViewedAt.
- Customer selection leaves lead Quoted.
- Confirm-booking moves lead to Converted and is idempotent.
- Full backend test suite and build pass.

### Frontend

- Playwright covers provider search returning the seven nearby Tartu providers.
- Multi-select -> outreach review -> confirm -> sent-history path.
- Draft create/reuse/delete path.
- Admin preview shows exact email recipient/body and customer page without navigation.
- Send review states all side effects and sends only after confirmation.
- Public `Request this offer` confirmation explains pending provider confirmation.
- Chosen state exposes `Confirm with provider and mark booked` to admin.
- Mobile 375x812 and desktop 1440x900 screenshots have no overlap or clipped actions.
- TypeScript, unit tests, build, and the complete Playwright suite pass.

### Deployment

No database migration is required. Deploy backend first because all frontend additions use
new backward-compatible endpoints. Deploy frontend after backend health checks. Production
canary verifies candidate counts, preview behavior, and draft deletion using a dedicated
test lead before the real lead is modified.

## 11. Documentation updates

Update `docs/CONCIERGE-OPS.md` and `docs/ROADMAP.md` so the documented loop distinguishes
customer selection from confirmed booking and describes nearby provider search, outreach
review, draft deletion, and delivery preview.

## 12. Non-goals

- Automatic provider reply parsing or inbound-email webhooks.
- Provider accept/decline portal links.
- A generic CRM, task manager, or sales pipeline.
- External city geocoding or a lead-coordinate migration.
- Automatic payment, contract, Booking, or Order creation after customer selection.
- Automatic outreach without an admin review.
